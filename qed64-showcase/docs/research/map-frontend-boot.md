## Risks
- The overrides are explicitly labelled dev-only (qed64-boot.ts:53,71,96). A future QED64 change could gate or remove them; docs/ARCHITECTURE-REEVALUATION-2026-09-02.md:93,207 shows they were once nearly deleted (T10/C11).
- Every runtime promotion invalidates the overlay: entries carry runtime and the worker refuses SNAPSHOT_UNPAIRED (lean.worker.js:1236-1246). After a promote, ?snapshots= alone breaks until a rebake, or until ?runtime=<old id> is added, which needs the old runtime manifest and chunks to still be served.
- Under the stock page, a ~1.3–1.5 GB raw superset 'mathlib' plus 122 MB init is malloc'd inside a 2 GiB initial commit (resident-session.ts:94; lean.worker.js:1280). The heap grows during or after the load, which is the repeated-grow path the code ties to nondeterministic renderer crashes. Only a custom policy (Option 2) can raise initialBytes.
- OPFS quota: the overlay 'mathlib' has a different digest, so its raw cache (`mathlib.<d16>.snapz.raw`, ~1.4 GB) sits beside the stock one (1.13 GB) in the same origin's 'qed64-snapshots' dir. Nothing in the page garbage-collects old raw entries (no removal found besides the stale-size check in snapshot-prefetch.worker.js:103).
- Vite dev (npm run dev) writes frontend/node_modules/.vite inside the read-only repo, and serve-dist.mjs can only serve snapshots placed inside qed64/public. Both violate the hard rules for the overlay; use your own server.
- serve-dist.mjs readFile()s whole artifacts into memory without Range support. That is fine for the 321 MB snapz but should not be copied for larger files; Node Buffers top out around 2–4 GB.
- A failed or misnamed ?snapshots= index fails silently at fetch (snapshots=null) and only surfaces later as "snapshot 'init' failed to load" through bootFailed and the crash breaker. Run the preflight first.
- localStorage 'qed64.buffer' is per-origin and is overwritten on every edit, so the gallery must rewrite it before every navigation. A user's own buffer on that origin is clobbered by the preload.
- A header whose imports are only non-umbrella roots (e.g. `import HasseView`) boots light and is never widened (main.ts:382). Demo snippets must carry an umbrella-root import or QED64.-rooted shims.
- Under a covered header the whole superset is in scope (playground semantics, docs/ARCHITECTURE.md:115-125). Widget demo names that collide with Mathlib/umbrella names trigger the collision note and the 'Load exact imports' offer, which restarts with the served essential pack and may not contain the widget modules.
- The first boot of the stock page also downloads the core pack (~120 MB of parts, ~390 MB unpacked to OPFS) regardless of the overlay (qed64-boot.ts:86-95).

## Open questions
- Untested: does the '/./snapshots/<file>' (or absolute-URL) entry trick, which reuses the served init without copying, work end-to-end in Chrome's worker fetch, the prefetch worker and the Cloudflare worker? The analysis rests on WHATWG dot-segment normalization.
- Untested: would a cross-origin snapshot URL in an index entry (e.g. a CORS-enabled bucket) load under COEP require-corp from the prefetch and Lean workers? fetch() defaults to cors mode, so CORS headers rather than CORP would be needed; not verified.
- Unknown: the actual heap high-water of a superset session (region plus Lean overhead) relative to the 2 GiB commit and the 6 GiB cap. It needs the browser experiment from the design study (§5 item 8).
- Unknown: whether Chrome requires COEP on dedicated-worker script responses in this setup, versus inheriting it. Mitigated by sending the headers on every response, as serve-dist and infra/worker.js do.
- Not audited in this area: whether node-runner.mjs (invoked by bake-snapshot.mjs) writes into the QED64 tree beyond --work and --out.
- Unknown whether R2 objects uploaded with Content-Type text/html under snapshots/ (same-origin gallery on the production QED64 worker) would be acceptable to the owner. It is technically a zero-source-change route but uses QED64's bucket.
